# WorkBuddy Token 用量看板

**解析 WorkBuddy 本地会话日志，把 token 消耗、缓存命中、credit 结算与响应速度还原成一张看得懂的看板**

---

WorkBuddy 本身不提供任何 token 用量视图。这个项目直接读取它在本地落盘的会话 JSONL  
（`~/.workbuddy/projects/**/*.jsonl`），起一个**零三方依赖**的解析服务和一个 Vue 3 看板，  
回答四个平时根本没法回答的问题：

- **钱花在哪了** —— credit 按项目 / 模型 / 会话 / 工具摊开，贵的那几个一目了然
- **缓存命中率什么时候掉的** —— 趋势图按「命中输入 / 未命中输入 / 输出」堆叠，  
  费用上涨究竟是量涨了还是命中率掉了，一眼分清
- **模型到底快不快** —— 本地**没有任何耗时字段**，吐字速度和每请求固定开销是从  
  事件时间线里推出来的（见[耗时是怎么算出来的](#耗时是怎么算出来的)）
- **时间花在哪了** —— 模型生成 / 工具执行 / 人的环节 / 离开电脑，四段互不重叠

技术栈：**Node.js（服务端仅用 `node:` 内置模块）+ Vue 3 + Vite + ECharts**。

> 下文截图与数字均来自 `npm run demo` 生成的合成数据（3 个虚构项目、2 个模型），  
> 不含任何真实使用记录。时间线按真实规律构造，所以耗时推导与速度拟合在演示数据上同样成立。

![会话详情](docs/screenshots/03-session-detail.png)

**本轮用量 + 会话轮次（抽屉顶部）。** 一次用户提问到回答之间往往夹着多次模型请求和  
工具调用，只看「单次请求」对不上一次提问的真实花销。这里按 `(sessionId, traceId)`  
把一轮的所有请求聚成一行：本轮卡片给输入、输出、缓存命中率、消耗积分（credit 实测值）、请求数与总 Token；  
下面按时间列出每一轮，点开可看该轮逐请求明细，还能一键跳到下方完整明细表定位。

几个刻意的口径与交互：

- 缺失 `traceId` 的请求**各自独立**成「未归属请求」，绝不并成一个空轮；
- 命中率分母为 0 时显示 `—`，不把「没有输入」画成 0%；
- 最近 5 分钟内有更新的轮次标为「活跃 · 最近更新」，**不**冒充「已结算」；
- 列表与展开明细都走定高虚拟窗口，几百轮也只渲染视口内的行；  
  `turnLimit` 裁剪时汇总仍覆盖全部轮次，界面会明说「仅显示最近 N 轮」；
- 自动刷新失败时保留上一拍数据，但顶部会出现提示条，不会让旧数字看起来是实时的。

**最近活跃摘要条（筛选栏下方常驻）。** 抬头就能看到最可能被关心的那一轮：  
会话标题、最近活动时间、本轮积分、累计积分、请求数与轮次数，四项指标随现有  
5 秒刷新链自动更新，点「查看详情」直接打开上面的抽屉。默认「跟随最近活跃」，  
多会话交替写入时目标会自己切过去；点「固定此会话」就锁住当前会话，  
别的会话再活跃也只给一句交代、不抢走视图，刷新页面后固定状态仍在。

界面一律叫「最近活跃」，**不叫「当前打开」**——本地日志里没有前台窗口信号。  
刚创建、还没有结算记录的会话会被识别，但只显示「尚无用量记录」的空态，  
不会摆一排假的 0 出来。

**请求明细：按 `messageId` 去重，展开可见耗时推导全过程**——  
端到端耗时 25s → 每请求固定开销 3.4s → 净出字时长 22s → 瞬时速度 252 t/s。  
任何一段算不出来都显示 `—`，而不是编一个数。

## 快速开始

环境要求：**Node.js ≥ 20**。无需数据库，无需任何三方服务。

### 一键启动（推荐）

直接双击项目根目录的 **`start-dashboard.bat`**。它会：打印本次使用的 node 绝对路径 →
必要时补构建前端 → 起服务 → 等 `/api/meta` 就绪后自动打开浏览器 → 保持窗口常驻。
**按 Ctrl+C 或关掉这个窗口即停止服务**。

之所以需要这个脚本：WorkBuddy 把 node 挂在**会话内临时注入的 PATH** 上，你自己的用户 PATH
里没有 `node` / `npm`，关掉对话后在普通终端敲 `npm start` 会报「不是内部或外部命令」。
脚本不按名字调用，而是显式写死绝对路径，并在启动窗口打印出来便于核对：

```
C:\Users\Administrator\.workbuddy\binaries\node\versions\22.22.2-6\node.exe
```

若 WorkBuddy 升级 Node 导致该路径失效，脚本会自动在
`%USERPROFILE%\.workbuddy\binaries\node\versions\` 下探测其它版本，打印
`AUTO-DETECTED fallback` 与实际路径；都找不到时才要求改脚本顶部的 `NODE_EXE`。

| 用法                              | 作用                                                                 |
| --------------------------------- | -------------------------------------------------------------------- |
| 双击 `start-dashboard.bat`        | 启动并自动打开浏览器                                                 |
| `start-dashboard.bat build`       | 先用同一个 node 重建 `web/dist` 再启动（改完前端用）                 |
| `start-dashboard.bat check`       | 只打印 node 路径 / 版本 / 数据源 / 产物状态，**不启服务**           |

脚本顶部还可改 `PORT`（默认 `5178`）；`web/dist` 缺失时会用同一个 node 自动构建一次；
设 `DASHBOARD_NO_BROWSER=1` 跳过自动开浏览器，取消 `FORCE_FULL_LOAD=1` 注释可回到全量加载路径。
窗口内已设 `chcp 65001`，服务日志的中文不会乱码。


### 交付产物与自检

`npm run build` 生成 `web/dist/`：`index.html` + `assets/` 下带内容 hash 的  
JS / CSS / 字体 / 图片，共 7 个文件、约 **861 KB**（2026-11-14 实测，阶段 2 视觉改版后）。它是**构建产物、不入库**  
（`.gitignore` 忽略 `dist/`），交付时随源码目录一起拷贝即可；  
换环境只需重跑一次 `npm run build`。

`npm start` 由同一个 Node 进程在 `http://127.0.0.1:5178` 同时提供 `/api/*` 与静态页面，  
不需要 nginx、Vite 或第二个常驻进程。启动日志会明确写出 `web/dist 已托管`；  
若产物缺失则提示先 `npm run build`，此时只提供 API。SPA 深链接与找不到的静态路径  
都回落到 `index.html`，`/api/*` 的未知路径仍返回 404。

**运行依赖只有三样**：Node.js ≥ 20、项目源码（含 `node_modules` 或 `npm ci` 重装）、  
一份可读的 WorkBuddy 会话日志目录。服务只读 `WORKBUDDY_HOME/projects/**/*.jsonl`，  
扫描状态写在项目内 `server/.cache/`，**不写入 WorkBuddy 目录、不修改其配置**；  
前端所有请求走同源 `/api`，源码里没有任何指向外部统计服务的请求；  
应用也不依赖 Agent 运行时，关掉对话后照常使用（用 `start-dashboard.bat` 启动，不需要 WorkBuddy 会话 PATH）。

在**干净目录**（无 `node_modules`、无 `web/dist`）按文档从零复现：

```bash

npm run build                       # 生成 web/dist
WORKBUDDY_HOME=/path/to/workbuddy npm start
curl -fsS http://127.0.0.1:5178/api/meta
curl -fsS http://127.0.0.1:5178/ | grep 'id="app"'
```

### 本地边界

解析服务默认**只监听 `127.0.0.1:5178`**，Vite 开发服务器也只监听 `127.0.0.1:5177`，  
局域网与其他网卡都访问不到。除了绑定回环，服务端还会：

- 校验 `Host` 头，拒绝非本机主机名（挡 DNS rebinding）；
- CORS 默认只允许回环地址上的本地来源，不再下发 `Access-Control-Allow-Origin: *`。

本机 `localhost` 会优先解析成 `::1`，所以文档、Vite 代理、E2E 与对账脚本统一写  
`127.0.0.1`。确需调整时可用环境变量（改动等于扩大可达范围，请自行评估）：

| 变量                 | 默认值         | 作用                        |
| ------------------ | ----------- | ------------------------- |
| `HOST`             | `127.0.0.1` | 监听地址                      |
| `PORT`             | `5178`      | API / 生产页面端口              |
| `CORS_ORIGIN`      | 回环白名单       | 追加逗号分隔的来源；显式写 `*` 才恢复任意来源 |
| `HOST_ALLOWLIST`   | 空           | 追加逗号分隔的允许 Host            |
| `SCAN_INTERVAL_MS` | `5000`      | 增量扫描间隔                    |

## 数据从哪来

WorkBuddy 把每个工作区的会话记录写成追加式 JSONL：

```
~/.workbuddy/projects/<项目目录名>/<sessionId>.jsonl
```

- `<项目目录名>` 是 cwd 的编码形式（如 `d-CODE-MyApp` 对应 `D:\code\MyApp`），  
  目录名只是兜底，每行里的 `cwd` 字段才是真值
- 追加写：文件只会变长，不会原地改写——这决定了可以增量解析

每一行是一个 JSON 对象，`type` 取值：

| type                    | 含义                  |
| ----------------------- | ------------------- |
| `session-meta`          | 会话元信息               |
| `ai-title`              | AI 生成的会话标题（看板里的会话名） |
| `message`               | 用户/助手消息，**可能带用量**   |
| `reasoning`             | 思考过程                |
| `function_call`         | 工具调用，**大部分用量在这里**   |
| `function_call_result`  | 工具返回                |
| `file-history-snapshot` | 文件快照                |

token 用量只挂在有真实请求的行上，位置是 `providerData.rawUsage`：

```jsonc
{
  "type": "function_call",
  "timestamp": 1790000000000,
  "sessionId": "3f9c2a1e-47b8-4d0f-9a51-c2e8d6b03a77",
  "cwd": "D:\\code\\webshop",
  "name": "Bash",
  "providerData": {
    "messageId": "01a9d3f2c8e41b675a209d1c3e8b7f11",   // 唯一键
    "traceId": "a71f3c02b5d94e8a",                     // 一轮对话，含多次请求
    "model": "deepseek-v4.1-flash",
    "rawUsage": {
      "prompt_tokens": 36945,               // 本次请求的输入
      "completion_tokens": 30382,           // 本次请求的输出（含思考）
      "total_tokens": 67327,
      "prompt_cache_hit_tokens": 8832,      // 命中提示缓存的输入
      "prompt_cache_miss_tokens": 28113,    // 未命中的输入（按全价计）
      "completion_thinking_tokens": 23690,  // 思考 token
      "credit": 2.14                        // 平台算好的结算单位 = 真实成本
    }
  }
}
```

## 五个必须踩准的口径

**1. 计数单位是 `messageId`，不是行数，也不是 `traceId`。**  
`messageId` 全局唯一，标识一次 API 请求；`traceId` 标识一轮用户对话，  
里面包含「思考 → 调工具 → 拿结果 → 再思考」的多次请求，会重复 1~58 次。  
按 `traceId` 计数会把用量少算几倍，看板统一以 `messageId` 去重。

**2. `rawUsage` 是单次请求的增量，不是累计值。**  
相邻两次请求的 `prompt_tokens` 从 36945 涨到 67363，是上下文随对话增长，  
不是"累计到 67363"，求和时直接相加即可。

**3. `credit` 就是成本，不需要自己维护价格表。**  
credit 和 token 数不成正比——一个真实例子：`kimi-k3-1` 6 次请求结算 107.2 credit，  
`deepseek-v4.1-flash` 404 次才 59.4，**6 次花掉的钱是 404 次的 1.8 倍**。  
自建价格表很难算准这种差异，直接用平台算好的 `credit` 反而最准。

**4. 一轮 = `(sessionId, traceId)`；缺 `traceId` 的请求各自独立成轮。**  
`/api/session` 的 `turns` 按轮聚合输入、输出、缓存命中/未命中、reasoning、credit  
与去重后的请求数；`turnSummary` 是全轮次合计，`latestTurn` 是最近一轮。  
三者与 `summary` / `steps` 使用**同一份筛选后的记录**，不会出现  
「KPI 是今天的、轮次是全历史」的口径分裂。  
日志里偶尔有不带 `traceId` 的用量行，它们按 `messageId` 各自成为  
`isOrphan: true` 的「未归属轮次」，绝不合并成一个空轮 —— 否则跨天的孤立请求  
会被错算成一次对话。`turnLimit`（默认 200、上限 500）只裁剪返回的列表，  
`turnSummary` 始终覆盖全部轮次；`steps[].turnKey` 与 `turns[].turnKey` 对应，  
前端可直接在本地按轮次下钻。

**5.「最近活跃」不是「当前打开」。**  
`/api/meta` 的 `latestActiveSessionId` 取三者最大值：会话文件的 `mtimeMs`、  
时间线最后事件、最后一条用量记录 —— 只看 credit 会让跟随滞后整整一轮，  
因为一轮开始时的用户消息和工具调用还没有结算记录。  
只有 `session-meta` / `ai-title`、既无事件也无用量的文件不参与候选，  
避免凭空冒出一个 0 消耗会话。本地日志没有 WorkBuddy 前台窗口信号，  
并发多个会话时只能知道「哪个文件最后被写过」；想锁定某个会话请用摘要条的「固定此会话」。

## 耗时是怎么算出来的

本地 JSONL **没有任何耗时字段**（把 13 个会话、4445 行、1162 条带用量的记录  
全字段枚举验证过）。但时间可以从事件时间线上推出来，只需要三个事实：

1. 一次请求 = 一个 `providerData.messageId`，且恰好只有一行带 `rawUsage`——  
   这一行的 `timestamp` 就是该次请求的**完成时刻**。
2. 请求的起点 ≈ 上一个**边界事件**（用户消息 / 上一条工具返回）的 `timestamp`，  
   两者相减 = 端到端耗时。
3. 工具耗时可以直接配对：`function_call.callId` ↔ `function_call_result.callId`，  
   实测几乎 100% 配得上（配不上的只有被中断的会话）。这是耗时维度里最硬的部分。

`reasoning` / `file-history-snapshot` 这类行的时间戳和请求完成点相差不到 20 毫秒，  
留在时间线上只会把 127 秒的生成时间错记到某个碎行头上，所以直接丢弃。

**直接相除是错的。** `输出 token ÷ 耗时` 会严重低估短请求，实测按输出量分桶：

| 输出 token       | 平均耗时  | 相除得到的"速度" |
| -------------- | ----- | --------- |
| 0 – 200        | 3.97s | 29 t/s    |
| 1 000 – 5 000  | 10.9s | 178 t/s   |
| 5 000 – 20 000 | 33.0s | 226 t/s   |
| 20 000+        | 128s  | 239 t/s   |

真相是 `耗时 ≈ 每请求固定开销 + 输出 ÷ 吐字速度`，所以用**最小二乘拟合**：  
斜率倒数就是吐字速度，截距就是固定开销。真实数据实测  
`deepseek-v4.1-flash`：斜率 → 250 t/s，截距 → 3.41s，R² = 0.96（n = 1154）。  
每条请求的**净出字时长 = 耗时 − 该模型固定开销**，短请求也能得到量级正确的瞬时速度。

两个口径必须分开说，混着展示会让人以为数字前后矛盾：

| 口径     | 定义                          | 用在哪        |
| ------ | --------------------------- | ---------- |
| 拟合吐字速度 | 全量样本拟合斜率，按输出量加权             | 看板主指标、模型明细 |
| 实测平均速度 | Σ输出 ÷ Σ净时长，**系统性偏低**（含调度空转） | 只作对照       |

已知限制：净出字时长里仍含 prefill（处理输入）的时间，未命中缓存输入很大的请求  
单条读数会被拉低；这一项主要落在截距里，不影响模型级斜率。想彻底分离需要把  
prefill 一起建模，但缓存命中/未命中两个字段高度共线，直接多元回归不收敛，留作后续。


**时间去向**把在岗时长拆成**模型生成 / 工具执行 / 人的环节**三段，阶段划分互不重叠：  
并行工具调用先来 `fc#1`、`fc#2` 再来 `fcr#1`、`fcr#2`，逐段累加正好等于  
`fcr#2 − fc#1`，不会因为工具并行而重复计时。

这个视图的几个口径都是按实测定的，不是拍脑袋：

- **叫「人的环节」而不是「等待用户」**。那段时间是你在读、在想、在组织下一句，  
  不是模型在空转。名字起错，读的人就会得出相反的结论。
- **30 分钟的「离开」阈值**：97 个人机间隔的长度从 1.1min **连续**铺到 23.8min，  
  唯一一个真实断层在 23.8min → 51.8min（×2.18），30 分钟正好落在断口里。  
  ⚠ 所以**没有**再分「90 秒 / 10 分钟」那种中间档——数据里不存在第二个断点，  
  硬切只会把"读一段长回复"误判成"离开"。
- **阈值实际上只作用于「人的环节」**：模型段最长 11.8min、工具段最长 5.1min，  
  都远够不到 30 分钟。所以"离开"判断天然只发生在"模型答完 → 你下一条消息"之间。
- **离开不画进条里**：离开一天能到 20 小时，画进去另外三段会被压成看不见的细线。  
  离开的量单独用文字交代。
- **「人的环节」里 ≥5 分钟的间隔单独报一个数**：是读长文档、去开会还是真的走开，  
  日志里区分不出来——如实交代，而不是替用户假设一个档位把它切掉。
- **每 credit 在岗 N 分**：在岗时长绝对值多少其实没意义，但"换 1 个 credit 要在岗多久"  
  可以横向比，这是把"这段时间花得值不值"变成可算的数的最小抓手。

**跨会话合成用并集（扫描线），不是相加。** 并行开两个会话时，同一段时间会被算两次：  
实测 15 个会话相加 107.5h，而真实墙钟（并集）只有 100.4h —— **虚高 7%**，并行越多错得越离谱。  
做法是把时间轴切成"活跃集合不变"的小段，每段按活跃会话数均分给各自的类型 ——  
这样 Σ三段 恒等于在岗时长（并集长度），占比才自洽。离开只在**没有任何会话在工作**时才计入，  
否则一个人去开会，会把另一个还在跑的会话的真实在岗时间也涂成"离开"。

**时间去向趋势**：按当前粒度分桶（先按桶边界切开区间再逐桶做扫描线，跨零点的段不会整段算进前一天）。  
只有一个总数时，"这周比上周怎么样"无从谈起 —— 绝对值多少不重要，趋势才可行动。

## 架构

```
浏览器 (Vue3 + ECharts, :5177)
    │  /api/*  （Vite dev proxy）
    ▼
解析服务 (Node http, :5178)
    ├── scanner.js   发现 projects/**/*.jsonl，增量续读（记录 + 时间线事件）
    ├── parser.js    行 → 规范化用量记录 / 时间线事件
    ├── timing.js    耗时推导：请求耗时、工具配对、阶段分解、速度拟合、扫描线并集
    ├── store.js     内存存储 + 过滤/分组/分桶聚合
    └── index.js     REST API + 每 5s 自动重扫
```

解析服务**只用 `node:` 内置模块**，没有 express、没有 sqlite，`npm start` 即跑。

**增量策略**：JSONL 是追加写的，按文件维护 `{ size, offset, mtimeMs }`——  
没变直接跳过；变大就从 `offset` 读尾巴、只解析新增行；变小判定被重写、整体重解析；  
且只处理到最后一个 `\n`，避免把正在写的半行解析掉。

**时间线事件也必须增量累积**：耗时的差值跨解析块——工具跑了几分钟，中间文件可能  
被追加过好几轮，某次请求的起点就落在上一次读进来的那段里。所以解析块除了吐记录，  
还要吐一份有序事件流（用户消息 / 带用量的请求 / 工具返回，其余行直接丢弃），  
攒齐之后才做配对；配对逻辑放在单行解析里的话，每条请求的起点都会丢。

**刷新链路（两段独立的定时器，缺一段都看不到实时数据）**：

| 环节             | 做什么                         | 周期                        |
| -------------- | --------------------------- | ------------------------- |
| 服务端 `index.js` | 增量重扫 JSONL，把新记录读进内存 `Store` | 5s（`SCAN_INTERVAL_MS` 可调） |
| 前端 `App.vue`   | 静默重取 `meta` + 当前页签 + 已打开的抽屉 | 5s，切到后台自动暂停、切回立刻补一拍       |

这点很容易踩：**只加服务端扫描，页面不会自己变**（页面只在挂载 / 筛选变化 / 点刷新时取数），  
看上去就像"自动扫描没生效"；反过来只加前端轮询，也只是把同一份旧数据反复拉下来。  
所以判断"自动更新有没有生效"，看顶栏那个「最近扫描」时间会不会自己往前走最快。

前端自动那一路走的是只读接口，**不调 `POST /api/refresh`**——强制重扫是手动按钮的语义，两边职责分开。

## 前端的几个取舍

**会话明细的窗口化渲染。** 单会话最多 331 次请求（实测），13 列全量铺开是 4300+ 个单元格；  
叠加 5 秒自动重取，整张表会跟着重渲染，滚动明显掉帧。现在只渲染视口内的行  
（固定行高 34px + 上下占位行撑出滚动高度），DOM 节点数与会话长度脱钩 ——  
331 条的会话实测只渲染 **19 行**。不引三方虚拟列表是因为需求只有"定高行 + 单列滚动"这一种，  
手写不到 30 行；引库反而要额外处理它和 sticky 表头、和 5 秒轮询的配合。

**上下文增长曲线用双 Y 轴。** 输入动辄上万 token、输出只有几百，量级差约 100 倍，  
合在一根轴上输出会被压成贴着底边的直线，等于没画。拆成左轴输入（堆叠面积，即上下文本身）、  
右轴输出（柱）。双轴唯一站得住的场景就是**同单位、不同量级** ——  
换成 token vs 百分比那种异单位双轴就开始骗人了。请求多时用底部滑块放大局部。

**筛选条件存 localStorage，只在当天生效。** 三条规则：  
① 隔天打开一律回默认 —— 还原出昨天的关键词，用户第一反应是"我明明没筛，数据怎么这么少"，  
这是记忆功能最经典的翻车方式；  
② 相对区间（今天 / 近 7 天…）**只存档位名**，还原时按"今天"重算，绝不冻结算出来的绝对日期，  
否则"近 7 天"第二天会变成"近 8 天"、档位高亮还对不上；  
③ 绝对条件（项目 / 模型 / 类型）先用 meta 校验一道，已消失的选项清回"全部"，  
避免空选择器 + 恒 0 条结果这种更让人困惑的状态。  
区间档位定义抽到 `web/src/utils/ranges.js`，FilterBar 与存储共用同一份 —— 两边各写一套迟早会对不上。

## API

|                                                                            |     |           |
| -------------------------------------------------------------------------- | --- | --------- |
| 统一支持 `from` `to` `projectId` `model` `kind` `keyword` `granularity`（\`hour | day | month\`）， |
| 所有视图口径一致：                                                                  |     |           |

| 端点                            | 用途                                                                                              |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET /api/meta`               | 数据源路径、可用筛选值、记录数、模型速度画像                                                                          |
| `GET /api/overview`           | KPI + 趋势 + 按模型/项目/工具分布 + 时间去向（含按粒度趋势）+ 工具耗时排行                                                   |

万一这次没删掉，下次运行开头的 sweep 会清（只清**一小时前**的，  
按时间筛是为了不误删并发运行的另一个 e2e）。

## 冷启动按需加载（阶段 1）

服务**不再在启动时全量读所有会话日志**。启动时只 `stat` 全部文件（毫秒级），完整解析
「近 7 天内有写入」的文件，其余冷文件只登记 `size / mtimeMs / birthtimeMs` 指纹、不读内容；
默认档位是「今天」，首屏零额外读盘。切到「近 30 天」「全部」或按日期自定义筛选时，服务端在
返回该请求前按 `birthtimeMs <= to && mtimeMs >= from` 双边界圈出候选冷文件、解析补齐，
数据到手才响应；页面同时给一条「正在读取历史数据」提示（不清空当前视图），筛选栏写
「已加载 N / M 个文件」。加载过的文件不卸载，重复切档不再读盘。

判断不依赖读内容，也不需要重建读取逻辑：`fs.stat()` 免费给的创建时间与修改时间就够了。
索引（`server/.cache/file-index.json`）只记汇总量（stat 指纹、真实首尾时间戳、模型集合），
**不写标题 / cwd / 提示词**；损坏、版本不符或换 `WORKBUDDY_HOME` 时丢弃并自动回退全量一次，
不作为正确性依赖。

真实数据实测（173 个 JSONL / 375 MB）：

| 场景 | 结果 |
| --- | --- |
| 冷启动 | 加载 **28 / 173** 个文件、解析 **43,657,521 B**（全量路径 398,451,060 B） |
| 默认「今天」首屏 | 13 ms，`loadedFiles` 与 `revision` 均不变 |
| 首次切「全部」 | 1,637 ms 补齐 145 个文件 → 173/173，`revision` 只 +1 |
| 再切回「今天」 | 零读盘，业务 KPI 与切档前逐字段恒等 |

一键回退到第一阶段的全量路径：`FORCE_FULL_LOAD=1 npm start`（回归夹具、排障用）；
`HOT_DAYS=N` 可改预热窗口（默认 7）。启动日志写「已加载 N / M 个文件 · 启动解析 X B」，
并区分「FORCE_FULL_LOAD=1」与「索引不可用」两种全量原因。

并行跑回归、或同时起多个指向不同 `WORKBUDDY_HOME` 的服务时，可用
`TOKEN_DASHBOARD_CACHE_DIR=<临时目录>` 把缓存指到别处，避免各实例互踩同一个
`file-index.json` 的 `sourceKey`；不设置时路径仍是 `server/.cache`。

两点边界：

- 切档补载会触发一次 `rebuild()`，`summary.netMs / measuredSpeed / speedSamples` 与
  `overview.speed` 随速度画像「越用越准」而变；积分、请求数、token、命中率、轮次、
  趋势分桶、最慢工具**逐字段恒等**。第一阶段每拍追加新记录时同样会变，不是新增的口径问题。
- 冷文件没读过就没有索引真值，若其创建时间被复制 / 备份还原改晚，历史单日筛选可能漏判；
  用 `npm run index:rebuild` 全量重建真值即可。内存按「加载过不卸载」，切「全部」后仍随
  历史总量增长，本期只解决启动等待、不解决内存上限。

`npm run perf:bench` 的合成夹具所有文件都是刚写的、没有时间分布，**测不出冷热差异**，
因此它固定带 `FORCE_FULL_LOAD=1`，基准数字仍可与第一阶段对照；冷启动收益以上面的真实数据实测为准。

## 明细排序（两处）

「会话版面 → 打开会话 → 逐次请求明细」与「明细版面 → 请求明细」的右上角各有一个
**时间排序 Tag**（`时间 ↓ 最新在前` / `时间 ↑ 最早在前`），点一下在逆序 / 正序间切换，
控件本身写明当前方向，交互与会话列表的可点击列头一致。两处**默认都是时间逆序**；
会话列表仍默认按 credit 降序，不受影响。

- 抽屉里的排序纯前端完成：`#` 始终表示「第几次请求」，不随排序翻转；
  「上下文增长曲线」恒按时间正序（横轴是请求序号），切排序不影响它；
  轮次「在完整明细中定位」会按当前顺序换算下标。
- 明细版面的排序走 `GET /api/requests?order=asc|desc`，由后端按**全局**时间顺序分页
  （不是只翻转当前页），切换后自动回到第 1 页；不传 `order` 时仍是原来的逆序口径。
- 顺序换算集中在 `web/src/utils/sortOrder.js`，两个位置共用
  `web/src/components/SortTag.vue`。

## 大数据表现

`npm run perf:bench -- --gen --tag=xxx` 会生成 20 项目 × 25 会话 × 200 请求 = **10 万条**用量记录，  
启动一个只绑回环的服务，实测冷启动、各 API、少量追加后的强制重扫与进程内存。  
所有计时都检查 HTTP 成功状态，追加段还逐次核对 `recordCount` 增加了对应条数，  
避免把错误响应或漏扫误记成性能提升。结果落在 `.perf/bench-<tag>.json`，  
可用 `--tag=before/after` 做前后对照。数据全是合成的，不读真实会话。

本机实测（Node 22，10 万条 / 500 会话）：

| 指标                    | 优化前                       | 优化后                |
| --------------------- | ------------------------- | ------------------ |
| 冷启动（全量解析 + 重建）        | 1062ms                    | 545ms              |
| 稳定态一拍（无新记录）           | 约 121ms（meta + 总览 + 会话详情） | **5.8ms（只取 meta）** |
| 单会话详情 API             | 7.1ms                     | 1.5ms              |
| 追加 1 / 10 / 100 条后的重扫 | 106 / 93 / 87ms           | 65 / 59 / 56ms     |

第 9 步在同样 10 万条 / 500 会话规模下重跑最终基准，并新增 `npm run perf:compare`：  
冷启动 **538ms**、稳定态 **6.1ms**、单会话详情 **1.6ms**、追加 1/10/100 条 **65.9/57.5/60.1ms**，  
与优化前终端基线相比分别下降约 **49% / 95% / 78% / 31~38%**，结果写入  
`.perf/bench-final.json` 与 `.perf/compare-final.json`。**优化前原始 JSON 已被初版 `--gen` 误删，  
基线数值来自首次终端实测输出，不能重新生成**；对照脚本明确打印这一来源，不把它伪装成可复现文件。

几个关键做法：`Store.records()` 不再每次查询都复制并排序全历史，rebuild 时排一次即可；  
单会话详情走 `sessionId` 索引；`/api/meta` 返回 `revision`，前端只有在「版本没变且上一拍  
全部同步成功」时才整拍跳过重取与重绘；失败会在下一拍重试，切页签会主动补齐最新版本。  
同 URL 的 GET 在飞行中复用同一个 Promise，手动刷新会等当前 poll 与旧 GET 收尾后再重扫；  
会话列表超过 200 行时只渲染前 200 行（组头小计仍按全部会话算），可「显示更多／显示全部」；  
全量轮次索引改成惰性——生产路由根本不读它，没必要每次 rebuild 都白算 3 万多个轮次并排序。

**已知边界**：少量追加时仍会全量重算耗时推导、速度拟合与派生字段，所以 1 条和 100 条的  
重扫耗时接近（约 55~65ms），成本仍是 O(N) 而非 O(新增量)。10 万条 / 5 秒扫描间隔下  
占空比约 1.2%，且只在写盘期间发生，当前可接受；要做成真正随新增量增长，需要按会话维护  
增量游标（跨块事件配对）、把 `netMs/tps` 改成按画像即时计算、并让轮次累加器可增量更新。  
这属于单独的数据引擎改造；若规模再上一个数量级，应先提交实测依据再决定是否引入 SQLite。

**第 9 步明确未覆盖**：ECharts tooltip 没有做鼠标悬停级交互断言——它是 canvas 坐标触发，  
坐标抖动会让验证本身变成噪声；现有改用「真实模板输出 → 浏览器 `innerHTML`」的确定性探针，  
并补了真实页面中的恶意标题文本显示。`App.poll()` 也没有独立组件单测框架；它由 live 的  
总览 503、抽屉首次失败、摘要条失败窗口与稳定态请求计数做浏览器级覆盖。  
性能优化前的原始基准 JSON 不可复现，已如实记录来源。干净环境安装与交付验收已在第 10 步完成，  
记录见[交付产物与自检](#交付产物与自检)。

## 故障排查

先看启动日志，它一次打印数据源、监听地址、页面产物状态、已解析条数与扫描间隔，  
多数问题在这一屏就能定位。

| 症状                                                                        | 原因与处理                                                                                                                                         |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm start` 报「不是内部或外部命令」／脚本提示 `No usable node.exe found`          | node 只在 WorkBuddy 会话临时注入的 PATH 里，不在你的用户 PATH。改用双击 `start-dashboard.bat`（显式绝对路径）；若连自动探测也失败，把脚本顶部 `NODE_EXE` 改成机器上真实的 `node.exe`。 |
| 页面空白、但 `/api/meta` 有数据                                                    | 没执行 `npm run build`，启动日志会写「未找到 web/dist」。构建后重启 `npm start`。                                                                                   |
| `Cannot find module @rollup/rollup-win32-x64-msvc` 或 `@esbuild/win32-x64` | npm workspace 漏装平台专用可选依赖：`npm i -D @rollup/rollup-win32-x64-msvc @esbuild/win32-x64`。两者已在根 `devDependencies`，换到 macOS / Linux 时删掉重新 `npm ci`。 |
| `Cannot find module 'token-dashboard-server'`                             | workspace 软链记录的是绝对路径，**移动过项目目录**。重新 `npm ci`（或 `npm install`）即可。                                                                              |
| `EADDRINUSE`                                                              | 端口被占：`PORT=5179 npm start`。注意 E2E、对账与 live 脚本默认连 5178，跑它们时要让服务回到默认端口。                                                                         |
| 启动后 0 条请求 / 0 个会话                                                         | `WORKBUDDY_HOME` 没指向含 `projects/` 子目录的位置；核对日志「数据源」行。演示数据用 `npm run demo`，它自动生成 `.demo/workbuddy`。                                             |
| 数字不更新                                                                     | 每 5 秒增量扫描一次（`SCAN_INTERVAL_MS` 可调）；可点「立即刷新」强制重扫。页面切到后台会暂停轮询，切回自动补拍。                                                                           |
| 顶部出现「自动刷新未成功」提示                                                           | 某一拍取数失败，保留的是上一拍数据；恢复后下一拍自动撤销，不需要刷新页面。                                                                                                         |
| 别的设备打不开 / 用 `localhost` 连不上                                               | 设计如此：只绑 `127.0.0.1`。本机 `localhost` 常优先解析成 `::1`，统一改用 `127.0.0.1`。确需扩大范围才动 `HOST` / `HOST_ALLOWLIST`。                                          |
| 跨域或自定义 Host 被拒                                                            | Host 头白名单与 CORS 回环白名单生效；用 `HOST_ALLOWLIST` / `CORS_ORIGIN` 追加，别用 `CORS_ORIGIN=*`。                                                             |
| 会话轮次或会话行"少了一截"                                                            | 轮次接口只取最近 200 轮（界面会写「仅显示最近 N 轮」，汇总仍覆盖全部）；会话主列表超过 200 行会截断，点「显示更多／显示全部」。                                                                        |
| 构建提示 chunk > 500 kB                                                       | ECharts 打进单个 chunk，已知且不影响运行；后续可做 `manualChunks` 拆分。                                                                                           |
| 昨天保存的筛选条件第二天不见了                                                           | 「记住筛选」按当天有效设计，跨天自动回到默认值。                                                                                                                      |
| 启动日志显示「已加载 28 / 173」、页面里历史项目/模型偏少                                         | 设计如此：只加载近 7 天，筛选栏有「已加载 N / M 个文件」交代。切一次「全部」或按日期筛到历史区间即补齐；想每次都全量用 `FORCE_FULL_LOAD=1 npm start`。                                     |
| 切「全部」第一次明显等一会儿                                                             | 首次要补读历史文件（真实数据约 1.6s），期间有「正在读取历史数据」提示且**当前视图不清空**；之后常驻，不再等待。                                                                        |
| 启动日志写「索引不可用…回退全量」                                                         | `server/.cache/file-index.json` 损坏、版本不符或刚换过 `WORKBUDDY_HOME`；本次自动全量加载并重建索引，只发生一次。也可 `npm run index:rebuild` 手动重建。                              |
| 10 万条数据下总览偶有卡顿                                                            | 稳定态每拍只取 `/api/meta`；有写入时 `/api/overview` 单次约 113ms，属已知边界（见下节）。                                                                                |

## 已知限制与后续增强

**统计口径**

- 不递归归属子 Agent 的用量；本期统计范围与上游一致，扩展会单独说明。
- 「最近活跃」按本地日志最后写入时间判断，**不识别 WorkBuddy 前台窗口**；固定会话被删除或换数据源时给空态，需手动切回跟随。
- 耗时与吐字速度是从事件时间线推导的，不是日志里的实测字段；首字延迟（TTFT）拿不到，样本不足的模型会标低置信。
- 速度画像（`speedProfiles` / `defaultOverheadMs`）按「当前已加载记录」在每次 `rebuild()` 时重拟合，`summary.netMs / measuredSpeed / speedSamples` 与 `overview.speed` 会随切档或新记录渐进；业务 KPI 不受影响。

**性能**

- 少量追加仍需 O(N) 全量重算耗时推导、速度拟合与派生字段，10 万条约 55~65ms；稳定态已由 `revision` 跳过重取，实测占空比约 1.2%，当前保留。
- 每次扫描仍会 `stat` 所有 JSONL 文件；`/api/overview` 单次约 113ms（稳定态不再调用）。规模再上一个数量级时先提交实测依据，再决定是否引入 SQLite。
- 「加载过不卸载」：切到「全部」后内存常驻全量数据，两年后估约 2.8 GB（常规强度）/ 6.6 GB（极端强度）。本期只解决启动等待，不解决内存上限。
- 合成性能夹具无时间分布，冷启动按需加载的收益只在真实数据上可测；`perf:bench` 固定走全量路径以保持前后对照。

**展示与验证**

- 虚拟窗口因 sticky 表头有约 1 行系统性偏移（`OVERSCAN=6` 兜住，不露白）；`turnLimit` 尾部裁剪时保持滚动位置会看到行内容左移；卡片与列表行的「活跃」判定在 5 分钟边界可能差一帧。
- ECharts tooltip 无鼠标悬停级交互断言，改用真实模板输出 + 浏览器 `innerHTML` 的确定性探针；优化前基准 JSON 已丢失，对照脚本明确标注数值来源为首次终端输出。
- 本期交付本地 Web 应用与 `web/dist`，**不制作 exe**；`web/dist` 是构建产物不入库，所有改动仍在工作区，未推送远程、未发布 Release。

后续增强项见[路线图](#路线图)，均不在本次交付范围内。
